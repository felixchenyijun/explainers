Lean: how a computer checks a mathematical proof

Lean checks whether a proof establishes your exact mathematical claim. Automation can find the proof for you—but it cannot settle every possible claim.

Three possible outcomes of a proof attempt:

Proof of P acceptedP is established from the assumptions.
Proof of “not P” acceptedP is refuted from the assumptions.
No proof foundThis attempt settles nothing.
01 / TESTS VS. PROOFS

Forty successes. One counterexample.

Suppose someone claims: “For every natural number n, n² + n + 41 is prime.” Natural numbers are 0, 1, 2, …; a prime is a whole number greater than 1 with no positive divisors except 1 and itself.

The claim we are testing
n² + n + 41

Try the first few inputs. How much confidence would 40 successes give you?

Each tile is an input n. ✓ = prime; × = composite; · = untested.

Untested claim

A test checks a particular input. The claim says “every input.”

A counterexample defeats “for every.” Many passing tests leave infinitely many inputs unchecked. A proof instead gives a reason that covers the whole domain. Exhaustive testing can prove a claim over a finite domain—if you really cover every case.

How can a short proof cover infinitely many numbers?

Prove a rule about an arbitrary n. To show n + 1 > n, you use how natural-number order works; you never need to choose a particular n. The argument is valid for whichever n is supplied.

Another way: induction is a proof about the next step

Imagine an endless row of dominoes. To establish a property for every natural number, prove it holds at 0, then prove that whenever it holds at n, it also holds at n + 1. Every natural number is reached from 0 by finitely many successor steps.

Both obligations need proofs. Checking the first dominoes, or assuming that the pattern continues, is not induction. Lean has an induction tactic that exposes these obligations.

02 / WHAT A PROOF IS MADE OF

A proof is a program that carries evidence.

Lean is both a programming language and a proof assistant. The bridge is types: 7 : Nat means “7 is a natural number”; h : P means “h is evidence for proposition P.” A proof is an expression whose type is the claim.

Start with a tiny theorem: if P and Q hold, then Q and P hold. Here P and Q stand for any statements. ∧ means “and”; → means “implies.”

Assemble the evidence
P ∧ Q → Q ∧ P
STEP 1 / 4

A claim is a required type.

To prove an implication, build a function: give it evidence of P ∧ Q, and it must return evidence of Q ∧ P.

theorem swap (P Q : Prop) :    P ∧ Q → Q ∧ P := by  intro h  exact ⟨h.right, h.left⟩

Proof state · ⊢ means “still need to prove”

P Q : Prop ⊢ P ∧ Q → Q ∧ P
Guided illustration, not a live Lean runtime.

Prop means proposition; swap names the theorem; := by starts a tactic proof.

“And” is a pair of evidence. “Implies” is a function between evidence. The proof works for any P and Q because it only rearranges what it is given. This connection is called propositions as types.

See the same proof written directly as a function
theorem swap_term (P Q : Prop) :
    P ∧ Q → Q ∧ P :=
  fun h => ⟨h.right, h.left⟩

fun h => … builds a function. h.right extracts evidence for Q; h.left extracts evidence for P. The angle brackets bundle them. The tactic script above builds equivalent evidence for the kernel.

Ordinary Lean programs calculate values; theorem proofs establish propositions. A function can even return a value together with a proof that the value meets a specification. Evidence need not be retained as data when a program runs.

03 / WHERE AUTOMATION FITS

Let a tactic find the evidence.

A tactic is a program that helps construct a proof. It can unpack assumptions, reuse theorems, simplify expressions, or solve a supported class of problems. The kernel still checks the resulting evidence.

Three worked examples

Adding one makes every natural number bigger.

n is arbitrary. omega reasons about natural-number and integer arithmetic.

import Lean

example (n : Nat) : n + 1 > n := by
  omega

Examples checked with Lean 4.33.0: five valid proofs accepted, two deliberate mistakes rejected. These controls reveal those outcomes; they do not run Lean in your browser.

To refute P, Lean needs a proof of ¬P. “Not P” means that assuming P leads to a contradiction. For a universal claim, one verified counterexample can supply that contradiction. A rejected proof is evidence about the attempt, not a refutation of its claim.

Where does AI fit?

In the “find evidence” box. An AI can suggest a formal statement or proof steps, inspect Lean’s feedback, and try again. Fluent prose is not a proof term. Its successful proof still needs checking, and a person must ensure the formal statement says what was intended.

Why no universal “true or false” button? Some restricted problems have algorithms that always decide them. All of mathematics does not: a perfect, always-terminating solver would also solve encoded halting problems, which is impossible. A failed search may simply need another idea; some statements are independent of a chosen axiom system.

A finished proof has no admitted holes such as sorry. Its exact statement and assumptions still need to match your question.

What a checked proof actually promises
Right statement
Lean checks the formal claim you wrote. A mistranslation can turn a hard question into an easy but irrelevant theorem.
Stated foundations
Results follow from their assumptions, definitions, and axioms. An inconsistent axiom can make any claim derivable. Use #print axioms theoremName to inspect dependencies.
No admitted holes
sorry means “accept this missing proof for now.” Lean warns, but the file may still compile. A theorem depending on sorryAx is unfinished.
A trusted checker
The kernel and its execution environment are part of the trust base. Ordinary tactics produce checked terms; native-computation shortcuts can add trust in the compiler/runtime. Acceptance is not a guarantee against every implementation or hardware bug.
