Kubernetes, from the inside out.

Kubernetes is a collection of control loops that continuously turn declared intent into running processes, even as machines and workloads change.

Conceptual simulation, not a live cluster. Steps serialize overlapping loops; deletion and propagation are compressed. Assigned specs are assumed cached by kubelets; Ready counts show worker observations. Capacity is explored below.

The powerful idea: failures and user edits both create a mismatch. The same repair loop handles both. There is no special, perfectly remembered “undo the failure” script.

Objects are contracts. A Deployment describes a rollout. A ReplicaSet maintains a population. A Pod describes one placement unit: one or more containers that run together. Ownership connects these contracts; labels and selectors connect sets of objects.

Processes are consequences. The scheduler only assigns a node. That node’s kubelet asks its container runtime to start processes. Control-plane coordination can stop while existing workloads and installed network rules keep working.

Under the API: why the loops converge

The API stores intentions and observations separately. A Deployment's spec.replicas: 3 is a target; status.readyReplicas: 2 is a reported observation. Status can lag reality. Controllers keep working toward the latest specification: changing three replicas to five and immediately to two does not require passing through five running copies. This level-based contract makes missed intermediate changes survivable. API conventions

An accepted write is the beginning of the work. The API server authenticates identity, authorizes the operation, applies admission rules and validates the object before persisting accepted state. Admission can inject defaults or reject unsafe configuration. A successful apply confirms an API change; scheduling, image pulls and application readiness still happen asynchronously. API access control

A watch wakes a loop; it does not dictate the answer. A typical controller maintains an informer cache using list/watch. Event handlers enqueue an object's namespace/name. A worker reads current cached state, compares it with intent, and makes a useful API change. Failed attempts return to the queue with backoff. A queue item means “reconsider this object,” rather than “replay this historical instruction.” Official controller implementation

Reconciliation must tolerate being repeated. If a controller restarts after creating a child, its next pass should discover that child instead of blindly creating another. Desired-state checks, ownership and retry handling make repeated attempts safe. This is an engineering requirement, not a guarantee that every side effect is automatically idempotent. External systems also need stable identities or other duplicate protection.

Concurrent writers use optimistic concurrency. An object carries a server-issued resourceVersion. A client performing a conditional update supplies the version it read. If another writer changed the object first, an outdated update fails with 409 Conflict; the client rereads and recomputes. Watches also use resource versions to track changes. If the requested history has expired, a client must rebuild its view. API consistency and watches

The tradeoff is durable coordination for delayed convergence. etcd persists API data; controllers and node agents coordinate through the API server. They can recover intent after restarting, and each loop can remain relatively small. The architectural consequence is that no single transaction atomically turns a Deployment into healthy processes across machines. API availability, observation delays and retries matter; convergence still requires available capacity and a satisfiable specification. Cluster components

From YAML to Linux processes

This illustrative manifest connects the abstractions. Replace YOUR_REGISTRY/checkout:v1 with your own pullable image: it must listen on 0.0.0.0:8080 and return HTTP 200 from /ready only when able to serve. That image is a placeholder, not an included demo application. Save as checkout.yaml, apply it, then inspect the rollout and endpoints.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: checkout
spec:
  replicas: 3
  selector:
    matchLabels: {app: checkout}
  strategy:
    rollingUpdate: {maxSurge: 1, maxUnavailable: 0}
  template:
    metadata:
      labels: {app: checkout}
    spec:
      containers:
        - name: api
          image: YOUR_REGISTRY/checkout:v1
          ports:
            - {name: http, containerPort: 8080}
          resources:
            requests: {cpu: "250m", memory: "128Mi"}
            limits: {cpu: "1", memory: "256Mi"}
          readinessProbe:
            httpGet: {path: /ready, port: http}
---
apiVersion: v1
kind: Service
metadata:
  name: checkout
spec:
  selector: {app: checkout}
  ports:
    - {port: 80, targetPort: http}
kubectl apply -f checkout.yaml
kubectl rollout status deployment/checkout
kubectl get pods -l app=checkout -o wide
kubectl get endpointslices -l kubernetes.io/service-name=checkout

The template creates a family. The Deployment manages ReplicaSets; a ReplicaSet maintains Pod objects. Their ownerReferences record parent identities for controller bookkeeping and garbage collection. Labels serve a different purpose: the Service's selector finds matching Pods regardless of which rollout revision created them. A Service does not own those Pods. Ownership

Binding becomes execution. After the scheduler assigns a node, its kubelet asks a container runtime such as containerd to prepare and run the Pod through the CRI gRPC interface. The runtime uses configured CNI plugins to set up Pod networking. Kubernetes supplies contracts; runtime and network implementations perform the machine-specific work. CRI · CNI

On a conventional Linux runtime, the result is isolated processes. Kernel namespaces shape their view of resources; cgroups account for and constrain consumption. Containers in a Pod share its network namespace, IP address and ports, so they communicate over localhost and cannot independently bind the same port. A Pod can contain multiple cooperating containers. Declaring containerPort describes the port; the application still has to create a listening socket. It does not expose a public endpoint. A Kubernetes Namespace, which scopes API objects, is a separate concept. Pod isolation and sharing

Requests and limits answer different questions. Here, scheduling budgets 0.25 CPU and 128 MiB per replica. These requests are not ceilings or dedicated cores. The CPU limit caps allowed CPU time through throttling; the memory limit can cause an OOM kill. A process can therefore be alive yet slow, or repeatedly restarted without replacing its Pod. Readiness then determines whether it should receive Service traffic. Resource enforcement

Restart, replacement, and rolling updates

A container exit in a Deployment usually triggers the kubelet’s restartPolicy: Always behavior: a new container instance, inside the same Pod, on the same node. Repeated failures introduce backoff. CrashLoopBackOff is a waiting reason shown by tools, not a Pod phase. Deleting the Pod is different: the ReplicaSet eventually creates a new Pod with a new UID. A Pod is scheduled once; it does not migrate between nodes. A bare Pod has no ReplicaSet to replace it.

3 × v1→3 × v1 + 1 × v2→v2 available→retire 1 × v1↻

Changing the Deployment’s Pod template creates a new revision and ReplicaSet. With replicas: 3, maxSurge: 1, and maxUnavailable: 0, each new Pod must become available before old capacity is reduced. Availability includes minReadySeconds if configured. Replicas that are still terminating can temporarily push resource use beyond the simple surge arithmetic.

If the new image never becomes ready, rollout progress stalls; old available replicas can keep serving under these settings. A progress deadline reports failure, but does not automatically roll back. A rollback is another change of desired template. Scaling only the replica count does not create a rollout revision. The Deployment controls process availability; backward-compatible schemas and application behavior remain your responsibility.

02 Stable names, replaceable destinations

A Pod’s IP is disposable. A Service gives a changing set of Pods a stable address. Its selector finds matching Pods; EndpointSlices describe their addresses and readiness. The cluster programs a data plane to deliver traffic.

Teaching model: deterministic selection, an in-cluster ClusterIP Service, ordinary readiness filtering, no session affinity. Real selection and packet handling depend on the data-plane implementation.

Control plane: learns which Pods match and publishes endpoints. Data plane: forwards actual traffic using installed state. The API server and etcd do not relay application requests.

Readiness asks “should I receive traffic?” Liveness asks “should this container be restarted?” A startup probe gives a slow application time to initialize before liveness and readiness probes begin.

Below the Service: DNS, packets, CNI, and ingress

For this ordinary Service, cluster DNS returns a virtual ClusterIP; the client opens a socket to that address. There usually is no application listening on the VIP. A Service implementation watches Service and EndpointSlice objects and installs forwarding rules. kube-proxy can program kernel packet handling; some cluster networking implementations replace it with eBPF-based handling. Endpoint choice and address rewriting may occur at different hooks. Existing connections typically retain their chosen backend through connection tracking; HTTP keep-alive can carry many requests on one TCP connection.

The Pod network supplies routable Pod addresses. In common Linux setups, a network namespace and virtual ethernet pair connect a Pod to host networking; routing, an overlay, or another implementation carries traffic across nodes. CNI is the plugin interface used by the runtime to set this networking up. CNI does not prescribe one universal packet path. NetworkPolicy enforcement also requires an implementation that supports it.

Service port: 80 mapping to targetPort: 8080 changes the destination port. Setting containerPort: 8080 in YAML is descriptive; it does not start a listener or expose a Service. Containers within one Pod share the Pod network namespace, IP, and port space and can communicate through localhost. A headless Service (clusterIP: None) instead lets discovery return individual endpoint addresses.

For external traffic, a LoadBalancer Service asks an integration to provision external access. HTTP host/path routing is typically provided by an Ingress controller or a Gateway API implementation. The Ingress API is frozen; Gateway API offers richer role and routing models. Neither API object forwards packets by itself, and installing the API without an implementation does not create a working gateway.

Readiness changes are not instantaneous connection drains. Endpoint publication and rule propagation take time; established connections may survive, and terminating-endpoint handling has extra semantics. Applications should handle termination gracefully. A preStop hook consumes part of the termination grace period; the runtime normally delivers the configured stop signal, commonly SIGTERM, before forced termination if necessary. Do not point liveness at every downstream dependency: one dependency outage can otherwise trigger a restart storm.

Primary details: Services · EndpointSlices · virtual IPs · DNS · Gateway API · probes.

03 A scheduler cannot manufacture capacity

The scheduler filters out nodes that cannot satisfy a Pod’s constraints, then scores the feasible nodes. Resource requests reserve scheduling capacity. Resource limits bound runtime consumption. Low CPU usage does not imply room for another reservation.

Resources, autoscaling, and the cost of overcommit

1000m is one CPU core’s worth of compute time. For an ordinary single-container Pod, a 500m CPU request counts as half a core for placement and helps determine CPU weight under contention. It is not necessarily a dedicated core. The container may use more when CPU is available. A CPU limit usually enforces a time quota: exhausting it causes throttling even if some CPU elsewhere is idle. Memory works differently: exceeding a memory limit can lead to an OOM kill; sustained node memory pressure can cause eviction. A request is not a wall around actual memory use.

The usable scheduling budget comes from node allocatable resources minus existing reservations. Summing simple app-container requests works for this lab; init containers, sidecars, Pod overhead, and newer resource features can change effective Pod requests. A limit specified without a request may be copied into the request, unless a defaulting mechanism sets one. The lab always supplies an explicit request, so changing the CPU limit leaves placement unchanged.

A HorizontalPodAutoscaler is another controller. For a basic CPU-utilization target, its rough calculation is desired ≈ ceil(current replicas × observed utilization / target utilization). Utilization is measured relative to CPU requests, so changing requests changes the signal. The real algorithm includes tolerance, missing metrics, readiness handling, bounds, and stabilization. It needs a metrics API provider; resource metrics are commonly supplied by Metrics Server. It adjusts desired replica count, not machine capacity.

A node autoscaler can respond to unschedulable Pods by provisioning suitable nodes; provisioning and application startup take time. More replicas cannot fix a saturated database, a restrictive placement rule, or a hard external rate limit. Affinity attracts Pods to eligible nodes; anti-affinity and topology spread distribute them. Taints repel Pods unless tolerated; a toleration permits placement but does not force it. Existing Pods generally stay where they were bound; changing desired layout does not teleport them.

Requests that are too high waste reservations; requests that are too low encourage overcommit and amplify contention. Useful tuning needs measured demand, a failure budget, and realistic startup behavior. Container limits, namespace quotas, and node capacity solve different problems.

Durable data, security, and the boundaries of self-healing

Separate a process’s lifetime from its data’s lifetime. A container’s writable layer is ephemeral. An emptyDir volume lasts with the Pod and can survive container restarts, but not Pod deletion. A PersistentVolumeClaim (PVC) requests storage; a PersistentVolume (PV) represents provisioned storage. A StorageClass describes how dynamic provisioning should happen, commonly through a CSI driver. Binding, attachment, and mounting involve further controllers and node components. Some storage waits for a consumer to be scheduled so volume topology and node placement can be coordinated.

A StatefulSet gives each replica an ordinal identity and can associate it with a stable claim. Replacing db-0 can reuse its identity and volume. This does not replicate data, elect a database leader, prevent split-brain, or create a backup. Access modes constrain mounting patterns; ReadWriteOnce means read-write on one node, not necessarily one Pod. Storage retention and reclaim policy determine what survives claim deletion. Treat those policies as part of the application’s data lifecycle.

Authorization and isolation are separate layers. A ServiceAccount supplies workload identity. RBAC maps subjects to allowed API verbs and resources through role bindings. A namespace scopes many object names and policies; by itself it does not block network traffic or provide a hard tenant boundary. NetworkPolicy supplies additive allow rules when the networking implementation enforces them. Without a policy selecting a Pod for a direction, that direction is generally not isolated.

A Secret is an API object with sensitive fields; base64 is encoding, not encryption. Encryption at rest must be configured appropriately, and API access must be constrained. ConfigMaps are for nonsensitive configuration. Projected file updates and environment variables have different refresh semantics: an environment variable in an already-running process does not update when its source object changes. Workload security also depends on unprivileged execution, capabilities, seccomp, host mounts, and admission controls.

Failure detection is not certainty. Heartbeats and timeouts cannot perfectly distinguish a dead node from a network partition. Existing processes may continue on an unreachable node while control-plane observations lag. Replacement and volume access need coordination; a distributed database still needs its own fencing and quorum rules. A PodDisruptionBudget constrains many voluntary evictions, such as a drain using the Eviction API. It does not prevent node crashes, and Deployment rolling updates follow their own rollout settings.

Primary details: volumes · persistent storage · StatefulSets · RBAC · NetworkPolicy · Secrets · disruptions.

A practical debugging path, and when Kubernetes earns its cost

Debug along the chain of contracts. API rejection: inspect validation, permissions, quota, and admission. Pending: inspect scheduling events, requests, constraints, and unbound claims. Assigned but not started: inspect image pulls, mounts, and runtime/network setup. Restarting: read the previous container’s logs, exit status, probes, and OOM reason. Running but unreachable: inspect readiness, labels, EndpointSlices, listening ports, DNS, and network policy.

kubectl get events -n demo --sort-by=.metadata.creationTimestamp

--previous needs a previous container instance; use -c for a particular container in a multi-container Pod. Events are temporary diagnostic records, not a complete durable audit log. kubectl top, where available, shows usage; it does not show the scheduler’s reservation arithmetic.

Kubernetes earns its cost when many workloads need shared scheduling, uniform deployment contracts, extensible automation, and repeatable recovery. The same object-and-controller pattern supports operators: a CRD adds a new API type, and a custom controller gives it behavior. A CRD alone does not run reconciliation.

The price is a distributed control system with lag, retries, interactions, upgrades, and many operational dependencies. For a small service, a managed application platform or a few processes on a VM may meet the need with less machinery. The engineering lesson worth keeping either way is durable intent plus small, retry-safe repair loops, with stable interfaces around disposable execution.
